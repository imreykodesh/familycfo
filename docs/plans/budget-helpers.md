## שלב 1א — כמה אפשר להוציא ביום

### מה המשתמש רואה

כרטיס בראש מסך הסקירה:

- **המספר:** "אפשר להוציא ₪X ביום עד {סוף התקופה}".
- **השוואה לקצב הרגיל:** "בדרך כלל אתם מוציאים ₪Y ביום על הוצאות משתנות". אם X קטן מ-Y, הכרטיס צבוע כ"חודש לחוץ".
- **מאיפה בא המספר:** יתרה עכשיו, הכנסות שעוד יגיעו, חיובים קבועים שעוד ירדו, כרית ביטחון, הפרשה לקופה לאירועים.
- **היום שמגביל:** אם ההגבלה היא יום לפני המשכורת ולא סוף החודש, כתוב "המגבלה היא ב-{תאריך}, לפני ש-{הכנסה} נכנסת".
- **אין מרווח:** אם החיובים הקבועים לבדם מורידים מתחת לכרית, במקום מספר כתוב "אין מרווח", וכמה חסר.

### החישוב (`src/analytics/allowance.ts`)

קו "רק קבועות": מתחילים מהיתרה בעו"ש היום, ומוסיפים רק כסף שידוע שייכנס או ייצא עד סוף תקופת התכנון
(`planningPeriod`: המחזור הנוכחי, או הבא כשנשארו פחות מ-5 ימים):

- פריטים קבועים מאושרים (משכורת, הוראות קבע, הלוואות) ותשלומים מתוכננים מהבנק, כמו בתחזית (`buildForecast`).
- חיובי כרטיס: **רק החלק הידוע** — עסקאות שכבר דווחו, תשלומים, קבועות בכרטיס ותשלומים מתוכננים
  (`knownAmount + projectedInstallments + projectedFixed + projectedPlanned`). ההערכה של קניות שוטפות שעוד לא נעשו
  (`typicalVariable`) **לא** נכללת, כי בדיוק אותה המספר היומי מחלק.
- לא נכללת ההערכה של הוצאות שוטפות מהבנק (`dynamicDailyRate`), מאותה סיבה.

לכל יום d מהיום ועד סוף התקופה: `זמין(d) = יתרה_קבועות(d) − כרית`, ומספר הימים עד אליו כולל היום `n(d)`.
הסכום היומי הוא הסכום הגדול ביותר שאפשר להוציא בכל יום בלי לרדת מתחת לכרית באף נקודה:

```
perDay = min over d of ( זמין(d) / n(d) ) − הפרשה_יומית_לקופה
```

היום שבו מתקבל המינימום הוא "היום שמגביל" (`bindingDate`).

- **הקצב הרגיל:** ממוצע ההוצאות המשתנות בחודשים המלאים האחרונים (`spendBaseline().dynamic`) חלקי 30.44.
- **המצב:** `none` כשהסכום ≤ 0, `tight` כשהוא קטן מהקצב הרגיל, אחרת `ok`.
- **הנחה שמרנית:** כל הוצאה יומית נספרת כאילו יצאה מהעו"ש מיד, גם קנייה בכרטיס שתחויב רק בחודש הבא.
- **מסנן בן בית:** בוחרים בן בית, והחשבון רק על חשבונות הבנק שלו.

### API

- `GET /api/allowance?member=ID`.
- גם בתוך `GET /api/summary` (שדה `allowance`), כדי שהסקירה לא תצטרך עוד קריאה.
- הצ'אט רשאי לקרוא (`API_PATHS`).

### בדיקות

הפונקציה הטהורה `computeAllowance`:
- היום שמגביל לפני משכורת.
- אין מרווח.
- הורדת ההפרשה לקופה.

## שלב 1ב — קופה לאירועים צפויים

### למה

חגי תשרי, פסח וחופש הגדול זזים בין החודשים הלועזיים משנה לשנה, ולכן ממוצע חודשי לא רואה אותם. החודש נגמר באפס,
ואז מגיע פסח. הקופה מחשבת כמה להפריש כל חודש כדי שכל אירוע יהיה מכוסה כשהוא מגיע.

### מה המשתמש רואה (מסך חדש `/seasonal`, "קופה לאירועים צפויים")

- **שלושה מספרים:**
  - יתרה בקופה (לחיצה מעדכנת אותה).
  - כמה להפריש בחודש.
  - האירוע הקרוב ובעוד כמה ימים.
- **רשימת האירועים:**
  - שם, התאריך העברי והלועזי הבא, בעוד כמה ימים.
  - הסכום הצפוי.
  - האם הקופה מכסה אותו כבר היום ✓.
  - הצעה מההיסטוריה: "בשנים קודמות יצא בערך ₪Z מעל חודש רגיל".
- **הוספה בלחיצה:** כפתורים להוספת האירועים הנפוצים (חגי תשרי, חנוכה, פורים, פסח, חופש הגדול), כל אחד עם סכום
  מוצע מההיסטוריה.
- **אירוע לועזי:** אפשר גם להגדיר אירוע לפי תאריך לועזי (למשל יום הולדת, או 1 בספטמבר לציוד לבית ספר).
- **אחרי שאירוע עבר:** האפליקציה שואלת "כמה יצא מהקופה על {אירוע}?". יש כפתור "כל הסכום", אפשר להזין סכום,
  או לבחור "לא השתמשנו". התשובה מורידה מהיתרה, וההתראה נסגרת.
- **בסקירה:** בכרטיס "כמה אפשר להוציא ביום" שורה "הפרשה לקופה לאירועים: ₪W בחודש", עם קישור למסך.

### החישוב (`src/analytics/hebcal.ts`, `src/analytics/seasonal.ts`)

**התאריך הבא של אירוע עברי:**
- `Intl.DateTimeFormat('en-u-ca-hebrew')` מפרק כל תאריך לחודש ויום עבריים. זה קיים ב-Node 22 וב-Electron בלי
  ספרייה חיצונית.
- סורקים יום-יום קדימה עד 400 יום.
- **שנה מעוברת:** "אדר" מתאים ל-`Adar` בשנה רגילה ול-`Adar II` בשנה מעוברת, כך שפורים תמיד באדר ב׳, ולעולם לא
  ל-`Adar I`.
- **יום שלא קיים השנה:** למשל ל׳ בחשוון בשנה חסרה. במקרה כזה לוקחים את היום האחרון של אותו חודש.

**כמה להפריש בחודש:**
- ממיינים את האירועים לפי התאריך הבא, ולכל אירוע k מחשבים:
  - `C_k`: הסכום המצטבר של כל האירועים עד אליו.
  - `m_k`: מספר החודשים עד אליו (`ימים/30.44`, לפחות 1).
- עם יתרת קופה P:
  ```
  perMonth = max over k of max(0, (C_k − P) / m_k)
  ```
- זה הקצב החודשי הקבוע הנמוך ביותר שמספיק לכל אירוע בזמן, לכל המועדים יחד. מעגלים כלפי מעלה לעשרות שקלים.
  אירוע מכוסה כשיתרת הקופה ≥ `C_k`.

**הצעה מההיסטוריה:**
- לוקחים כל מופע של האירוע ב-3 השנים האחרונות שיש עליו נתונים.
- סוכמים את ההוצאות המשתנות (לא קבועות) בחלון של 29 יום: 21 יום לפניו, היום עצמו ו-7 ימים אחריו.
- מחסירים מזה "יום רגיל" כפול 29. יום רגיל = ממוצע ההוצאות המשתנות ליום ב-120 הימים שלפני החלון, בלי 10% הימים
  העמוסים ביותר (כדי שקנייה חד-פעמית לא תנפח אותו). חציון לא מתאים כאן, כי במשפחה שקונה פעמיים בשבוע הוא יוצא כמעט 0.
- ממוצע העודפים (מופע בלי עודף נספר כ-0), מעוגל ל-₪50. מופע שאין לפניו לפחות 30 יום של נתונים לא נספר.

**סגירת אירוע שעבר:**
- המופע האחרון שתאריכו עבר הוא "ממתין להכרעה" כשהוא:
  - אחרי `settled_through`, כלומר התאריך של המופע האחרון שהמשתמש כבר הכריע עליו;
  - ואחרי יום יצירת האירוע.
- ההכרעה מורידה את הסכום מיתרת הקופה ושומרת את התאריך.

### נתונים (מיגרציה 18)

```sql
ALTER TABLE sinking_funds ADD COLUMN kind TEXT NOT NULL DEFAULT 'general';   -- general | seasonal (קופת האירועים)
CREATE TABLE seasonal_events (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  calendar TEXT NOT NULL DEFAULT 'hebrew' CHECK (calendar IN ('hebrew','gregorian')),
  month TEXT NOT NULL,        -- hebrew: Tishri … Elul (Adar = אדר / אדר ב׳); gregorian: '1'..'12'
  day INTEGER NOT NULL CHECK (day BETWEEN 1 AND 31),
  amount REAL NOT NULL,       -- the expected cost of one occurrence (positive ILS)
  active INTEGER NOT NULL DEFAULT 1,
  settled_through TEXT,       -- the last occurrence (YYYY-MM-DD) the user said how much it took from the pot
  notes TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
```

- **יתרת הקופה** נשמרת בשורה של `sinking_funds` עם `kind = 'seasonal'`, ונוצרת באירוע הראשון.
  היא לא נכנסת לחלוקת "חיסכון מומלץ" (`savingsCapacity`), כי ההפרשה אליה מחושבת כאן ומורדת מהסכום היומי.

### API

| נתיב | מה |
|---|---|
| `GET /api/seasonal` | האירועים עם התאריך הבא, הכיסוי, ההכרעה הממתינה וההצעה מההיסטוריה; הקופה; ההפרשה החודשית; הצעות לאירועים נפוצים שעוד לא נוספו |
| `POST /api/seasonal` | `{name, calendar, month, day, amount, notes?}` |
| `PATCH /api/seasonal/:id` | אותם שדות + `active` |
| `DELETE /api/seasonal/:id` | |
| `POST /api/seasonal/:id/settle` | `{date, spent}`: מוריד מהקופה ושומר `settled_through` |
| `PUT /api/seasonal/pot` | `{balance}`: עדכון יתרת הקופה |

- **הצ'אט:** רשאי לקרוא את `seasonal`, ולשנות את `seasonal`, `seasonal/ID`, `seasonal/ID/settle` ו-`seasonal/pot`.
- **התראות:**
  - `seasonal_settle`: אירוע עבר וממתין להכרעה.
  - `seasonal_short`: אירוע בעוד 45 יום או פחות, והקופה לא מכסה אותו.

### בדיקות

- תאריך עברי הבא:
  - פסח 5787 = 22.4.2027.
  - פורים בשנה מעוברת יוצא באדר ב׳.
  - יום שלא קיים בחודש.

## שלב 2 — סגירת חודש ודוח חודשי

### מה המשתמש רואה

מסך `/month-close` (או לשונית בתזרים). בתחילת כל חודש, על החודש שהסתיים, מוצגת רשימת בדיקות:

1. **לכל חשבון יש תנועות עד סוף החודש** (`dataCoverage`). חשבון שנעצר לפני הסוף מקבל כפתור "לעדכן עכשיו".
2. **אין כפילויות פתוחות** (`findDuplicateCharges`).
3. **אין הוצאות בלי קטגוריה.** יש קישור ל-`/transactions?review=1&cycle=…`.
4. **חיוב קבוע שלא הופיע החודש** (פריט מאושר ב-`scheduled_items` או סדרה פעילה ב-`recurring_series`) מקבל שאלה
   ולא מסקנה, עם שלושה כפתורים: "הסתיים", "עוד יגיע", "שולם אחרת".
   - "הסתיים" מסמן את הפריט `dismissed`, והדוח מראה כמה כסף התפנה בחודש.
5. **קישורי החזר שממתינים לאישור** (`transaction_links` במצב `suggested`).
6. **לכל בדיקה יש "✓ זה בסדר",** והאישור נשמר לאותו חודש.

כפתור "סגור את {חודש}" שומר צילום מצב ב-`month_closes.snapshot_json`: הכנסה, הוצאה, קבועות, משתנות, לפי קטגוריה,
מספר התנועות וסכום מוחלט לזיהוי שינוי. אם תנועות השתנו אחרי הסגירה, מופיע "נסגר ב-X, ומאז השתנו בו תנועות", עם
"סגור שוב".

**הדוח החודשי** הוא עמוד שניתן להדפסה (`@media print`). הוא מציג:
- את התשובה בראש: נשאר או חסר, וכמה.
- מול הממוצע.
- שלוש הקטגוריות שחרגו.
- התחייבויות קבועות.
- חובות.
- ההמלצות הפתוחות.
- מה התפנה מחיובים שהסתיימו.

### נתונים

- `month_closes` קיימת: שורה = חודש סגור (צילום מצב וחתימה). פתיחה מחדש מוחקת את השורה.
- טבלה חדשה `month_close_checks` (מיגרציה 19): התשובות לבדיקה 4 והאישורים לבדיקה 6, נשמרות גם לפני הסגירה.

### API

- `GET /api/month-close?cycle=`: הבדיקות והמצב.
- `POST /api/month-close/:cycle`: סגירה.
- `PUT /api/month-close/:cycle/checks`: תשובה או אישור לבדיקה בודדת. `DELETE /api/month-close/:cycle`: פתיחה מחדש.
- `GET /api/month-report?cycle=`.

### הצ'אט

- ה-skill `monthly-review` משתמש בדוח במקום לחשב לבד.
- קישור `/month-close?cycle=`.

## שלב 3 — סימולטור

מסך `/simulator`. שום דבר במסך לא נשמר ולא נוגע בנתונים.

### קיצוץ לפי קטגוריה

- בוחרים קטגוריה ומקבלים את הממוצע החודשי שלה (חודשים מלאים בלבד, `cashflowHistory`).
- מחוון "לקצץ ב-₪" מראה את החיסכון בחודש, בשנה, ובכמה חודשים יקדים כל יעד חיסכון (`sinking_funds.goal_*`).
- אפשר לצבור כמה קטגוריות.

### החזר חובות: כדור שלג מול מפולת

על `liabilities` עם יתרה אחרונה (`liability_snapshots`), ריבית ותשלום חודשי.

- **הקלט:** תוספת חודשית מעבר לתשלומים הקבועים. כפתור "קח מהקיצוץ" מעביר לכאן את סכום הקיצוץ.
- **השוואה לבסיס:** כל חוב לחוד עם המינימום בלבד, כשתשלום של חוב שנסגר לא עובר לחוב אחר.
- **הסימולציה, חודש אחרי חודש:**
  1. ריבית.
  2. הצמדה (`index_type = 'cpi'` עם מדד שנתי משוער).
  3. מינימום לכל חוב.
  4. העודף, כולל המינימום של חובות שנסגרו, הולך לחוב הראשון בתור.
- **סדר התור:**
  - כדור שלג: היתרה הקטנה קודם.
  - מפולת: הריבית הגבוהה קודם.
- **הפלט לכל שיטה:**
  - חודשים עד סילוק.
  - ריבית כוללת, ועלות ההצמדה בנפרד.
  - חיסכון מול הבסיס.
  - סדר הסגירה.
- **עמלת פירעון מוקדם** משוערת היא שדה רשות.
- **הסתייגות:** "אומדן לפי ההנחות — לפני פירעון מוקדם לבקש מהבנק דוח סילוקין".

### מימוש

- `src/analytics/simulator.ts`: פונקציות טהורות בלי imports, `debtPlan(debts, extra, method, assumptions)`, `compareDebtPlans` ו-`cutImpact(monthly, goals)`.
  המסך מייבא את הקובץ ישירות (ב-`web/vite.config.ts` מותר רק הקובץ הזה מחוץ ל-`web/`).
- `src/analytics/simulatorBase.ts` ← `GET /api/simulator/base`: ממוצעים לפי קטגוריה, יעדי החיסכון והחובות.
  הלוואה בלי יתרה, ריבית או החזר חודשי מופיעה ברשימת "לא נכללו" עם הסיבה. ההחזר נלקח מ-`monthly_payment`, ואם חסר, מהפריט הקבוע שמקושר להלוואה.
- החישוב עצמו רץ בדפדפן, כדי שהמחוון יגיב מיד. לצ'אט: `GET /api/simulator/debts?extra=&cpi=&fee=` מריץ את אותה השוואה בשרת.
- **מדד משוער:** 2.5% בשנה כברירת מחדל, ניתן לשינוי במסך.
- **תקרה:** 600 חודשים. החזר שלא מכסה את הריבית לא נגמר לעולם, וכך הוא מוצג.
- **הזולה יותר:** השיטה עם העלות הכוללת (ריבית + הצמדה + עמלות) הנמוכה. כששתי השיטות יוצאות זהות (למשל חוב אחד), אף אחת לא מסומנת.
- **הדגמה:** `npm run demo` מוסיף הלוואת רכב צמודה למדד ויעד חיסכון "רכב חדש".
- הבדיקות (`tests/simulator.test.ts`) משוות למקרים שחושבו ידנית.

## שלב 4 — בדיקת תקינות

מסך `/health`, עם מספר אדום ליד הכפתור בתפריט שסופר רק את הבעיות, לא את ההצעות. לכל שורה יש כפתור פעולה ו"התעלם".
ההתעלמות נשמרת לפי הנוסח המדויק, כך שהשורה חוזרת אם המצב משתנה.

| בדיקה | מקור |
|---|---|
| המשיכה האחרונה של כל בנק הצליחה; כמה כשלונות ברצף | `/api/sync-status` |
| גיל הגיבוי האחרון | `src/db/backup.ts` |
| אחוז ההוצאות בלי קטגוריה | `loadTransactions` |
| כפילויות אפשריות | `findDuplicateCharges` |
| חודשים בלי נתונים באמצע ההיסטוריה | `dataCoverage` |
| הצעות לכללי סיווג (תיאור שסווג ידנית 3 פעמים לאותה קטגוריה) | `transactions.category_source = 'manual'` |
| קישורי החזר והוצאות מתוכננות שממתינים | `transaction_links`, `planned_items` |
| כרטיס בלי חשבון חיוב | `accounts.billing_bank_account_id` |
| יתרה שלא התעדכנה מעל 3 ימים | `forecast.warnings` |

- **נתונים:** `settings.health_ignore` (JSON: מזהה בדיקה ← הנוסח שהוסתר). אין טבלה חדשה.
- **API:** `GET /api/health`, `PUT /api/health/ignore` `{id, ignore}`.

### כפי שמומש (`src/analytics/health.ts`)

- **משיכות:** רק חברות שיש להן חשבון פעיל. נכשלה = בעיה, עם ההסבר בעברית וקישור ליומן.
- **גיבוי:** רק באפליקציית הדסקטופ (רק היא מגבה). אין גיבוי, או שהאחרון ישן מיומיים = בעיה.
- **בלי קטגוריה:** הוצאות 90 הימים האחרונים. 5% מהכסף ומעלה = בעיה, פחות מזה = הצעה.
- **כפילויות:** 45 הימים האחרונים (`findDuplicateCharges`).
- **חודשים חסרים:** לכל חשבון שבדרך כלל יש בו לפחות 5 תנועות בחודש (חציון), חודש בלי תנועות בין הראשון לאחרון.
- **קישורי החזר:** כל קישור בשורה משלו, עם "כן, זה החזר" / "לא קשור" (`PATCH /links/:id`). עד עכשיו לא היה מסך שמאשר אותם.
- **הוצאות מתוכננות:** שבוע אחרי התאריך ועדיין לא חויבו ← `/fixed#planned`.
- **כרטיס בלי חשבון חיוב:** כשגם הזיהוי האוטומטי (`inferBillingAccounts`) לא מצא ← `/settings#accounts`.
- **יתרה ישנה:** חשבון עו"ש שהיתרה שלו מלפני יותר מ-3 ימים.
- **כללי סיווג:** סוחר שסווג ידנית 3 פעמים לאותה קטגוריה ואין כלל שמכסה אותו. הכפתור יוצר כלל (`POST /rules`) ומחיל אותו גם על הקיימות.
- **הכפתורים** הם קריאות API שהשורה נושאת (`actions`), כך שהמסך לא צריך לדעת מה כל בדיקה עושה.
- **הדגמה:** `npm run demo` מוסיף היסטוריית משיכות שבה המשיכה ממקס נכשלה פעמיים.
- **בדיקות:** `tests/health.test.ts`.

## שלב 5 — מעבר כרטיס/בנק ואימות ביטול

### מה המשתמש רואה

- **לפני המעבר:** "עוברים מכרטיס X לכרטיס Y". המערכת מייצרת לבד את הרשימה מ-`recurring_series` הפעילות של X:
  מנויים, ביטוחים, חוגים, הוראות קבע. לכל שורה מוצגים סכום, יום בחודש, טלפון/אתר אם ידוע, ו-✓ "הועבר".
- **אימות אוטומטי** אחרי כל משיכה:
  - החיוב הופיע ב-Y: ✓ "הגיע לכרטיס החדש".
  - החיוב הופיע שוב ב-X: ⚠ "עדיין יורד מהכרטיס הישן".
- **ביטול:** אותו מנגנון לחיוב שהוחלט לבטל, למשל מתוך ההמלצות. אם החיוב חוזר אחרי הביטול, נוצרת התראה
  `cancel_failed`. זה סוגר פער קיים: היום אין מעקב שמוודא שחיוב שבוטל באמת הפסיק.

### נתונים

טבלה `charge_moves`:

| עמודה | תוכן |
|---|---|
| `id` | |
| `recurring_series_id` | |
| `merchant_key` | |
| `from_account_id` | |
| `to_account_id` | null = ביטול |
| `status` | `todo` / `moved` / `verified` / `failed` |
| `marked_at` | |
| `verified_at` | |
| `notes` | |

- **צעד חדש ב-pipeline:** `verifyChargeMoves`, אחרי `refreshRecurring` (שמריץ את `detectRecurring`).

### כפי שמומש (מיגרציה 20, `src/analytics/chargeMoves.ts`, מסך `/charge-moves`)

- **העמודות בפועל:** כמו בטבלה, ובנוסף `description`, `amount`, `day_of_month` (כדי להציג ולבדוק גם אחרי שהסדרה הישנה נעלמת). `evidence_txn_id` שומר את התנועה שאימתה או הכשילה.
- **הרשימה:** הסדרות הפעילות של החשבון הישן (מנוי, חשבון, הלוואה) שמופיעות עד 6 פעמים ב-130 יום, כלומר בערך פעם בחודש. סופר שקונים בו כל שבוע לא מוצע.
- **"הועבר" / "בוטל"** שומר את התאריך (`marked_at`). "עוד לא" מחזיר לרשימה, ו"טיפלתי שוב" מתחיל את הבדיקה מחדש מהיום.
- **אימות מעבר:** חיוב מאותו בית עסק בחשבון החדש (שמות קצת שונים בין חברות האשראי נחשבים אותו בית עסק), בסכום ±25%, מ-14 יום לפני הסימון.
- **אימות ביטול:** עבר יום החיוב הרגיל + 5 ימים, והחשבון עודכן אחרי זה, בלי חיוב.
- **נכשל:** חיוב מבית העסק בחשבון הישן אחרי יום הסימון (±50%, כדי שעליית מחיר לא תסתיר אותו). נבדק גם אחרי אימות, כך שחיוב שחוזר אחרי ביטול מקפיץ `cancel_failed`. במעבר: `move_still_on_old`.
- **ב"תובנות והתראות":** כפתור "ביטלתי" ליד כל מנוי, ואחריו מופיע המצב (בבדיקה / ✓ נפסק / ⚠ חויב שוב).
- **התראת "מנוי חדש"** לא קופצת על חיוב שהועבר בכוונה לכרטיס החדש.
- **מספר טלפון / אתר:** אין לאפליקציה מקור לזה, ולכן לא מוצג.
- **הדגמה:** רשימת מעבר של שלושת המנויים מישראכרט למקס.
- **בדיקות:** `tests/chargeMoves.test.ts`.
