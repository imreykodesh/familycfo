# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Before any task read [PROJECT_MAP.md](PROJECT_MAP.md)** (files, screens, API routes, tables, settings / storage keys, scripts) and keep it up to date in the same task. Working rules: `.kiro/steering/` (also `.cursor/rules`) — answer the user in Hebrew, check with `npm run check`, everything ends on `main`.

## Commands

```bash
npm run scrape     # Scrape all banks once, then run the pipeline (SCRAPE_ONLY=isracard,max to limit; months back = SCRAPE_MONTHS ?? setting scrape_months_back ?? 3; SCRAPE_FROM=2026-01-01 to backfill, SCRAPE_FROM=max for as much history as each company gives; SHOW_BROWSER=0 headless; SCHEDULE="0 7 * * *" to keep running on cron)
npm run dev        # Household app: API (127.0.0.1:4310) + web UI (http://127.0.0.1:5180)
npm run pipeline   # Re-run classification / recurring / suggestions / alerts without scraping
npm run migrate    # Apply DB migrations (also runs automatically on open)
npm test           # Vitest unit tests (in-memory SQLite)
npm run typecheck  # API typecheck; web: npm --prefix web run typecheck
npm run check      # The gate before a commit (scripts/check.mjs): install if needed → typecheck API + desktop + web → tests (-- --clean, -- --skip-tests)
npm run demo       # Build demo.db with made-up data; npm run dev:demo runs the app on it
npm run desktop:dev   # The desktop app (Electron) from source: builds web/dist + bundles, data in "<appData>/FamilyCFO (dev)" (BANK_DB=demo.db to use the demo)
npm run desktop:pack  # Unpacked app in release/ for this OS; desktop:dist = installers (mac dmg/zip, win nsis, linux AppImage/deb)
build-windows.cmd     # Double-click on Windows: typecheck → web build → desktop bundle → release\FamilyCFO-<version>-x64.exe
# Release: bump package.json version, push tag vX.Y.Z → .github/workflows/desktop.yml builds mac/win/linux on their own OS and uploads to a draft GitHub Release
```

## Architecture

Israeli bank scraper + local household-finance app for a family (members are configurable in Settings). Everything runs locally; the API binds to 127.0.0.1 only and has no login.

- `src/scraper.ts` — `israeli-bank-scrapers` (npm release). Fetches 3 months back (`SCRAPE_FROM` / `POST /api/scrape {from}`: a date or `max` = 5 years, which each company clamps to what its site gives) + 2 future months (upcoming card charges/installments), raw data, and scraper categories. Hapoalim OTP is prompted in the terminal.
- `src/db/` — `connection.ts` (opens + migrates), `migrations.ts` (numbered, `schema_version`), `ingestRepo.ts` (saves scraped accounts; never overwrites user-edited fields).
- `src/ingest/` — `normalize.ts` (identity: bank reference + installment number, else legacy md5 + an occurrence suffix so identical same-day purchases are kept), `classify.ts` (rules → description cache → scraper category → external API; derives `kind`), `transfers.ts` (card-bill reconciliation, own-account transfer pairing).
- `src/analytics/` — pure functions over `loadTransactions()` in `common.ts`: cash flow, budgets, recurring detection, scheduled-item suggestions, day-by-day forecast per bank account, card charges & installments, paybacks (Bit/refund links), savings capacity & tight-month plan, net worth (FX via Bank of Israel), alerts, recommendations.
- `src/pipeline.ts` — runs after every scrape: FX → categorize → kinds → card bills → transfers → recurring → scheduled suggestions → paybacks → alerts.
- `src/server/` — Fastify API (`crud.ts` generic routes + `routes/transactions.ts`, `routes/analytics.ts`).
- `src/server/agent.ts` + `src/agent/mcp.ts` — the data chat (✨ in the header): each message runs the user's own `claude -p` (or Gemini / Kiro, below) (subscription, `ANTHROPIC_API_KEY` removed) with all built-in tools disabled and only the `household` MCP server (`api`: whitelisted GET endpoints, `sql`: SELECT on a read-only connection, `change`: POST/PUT/PATCH/DELETE on whitelisted API endpoints — never the scrape, the OTP or the chat). Changes go through the API so its rules hold (manual edits are marked manual). The UI refreshes its queries after an answer that changed data; links in answers (`/…`) open a screen, `ask:…` links send a quick reply. Streams to the UI as SSE; `--resume` continues a conversation. Its instructions (`agent/CLAUDE.md`) and skills (`agent/.claude/skills/`) are copied to a temp work dir per message (outside the repo, so this file isn't loaded); `--tools Skill --setting-sources project`.
- Insurance (`src/server/routes/insurance.ts`, page `/insurance`): policies + documents; files in `data/policies/<policy id>/` (git-ignored, `POLICIES_DIR` overrides). Actual cost = charges matching the policy's `match_pattern` (and `payment_account_id`, when set) in the last 12 months. Bulk import from a JSON spec (fields + documents + asset values): the screen's "ייבוא דוח" (`POST /api/insurance/import`, documents looked up in `data/reports`) or `npm run import:insurance -- data/reports/<file>.json` (idempotent). The chat reads documents with `Read`, limited to a `docs/` copy of `data/policies` + `data/reports` by a PreToolUse hook (`src/agent/guard-read.mjs`, symlinks resolved).
- Pension & long-term savings (`/pension`, `src/server/routes/pension.ts`): pension / study / provident funds are `assets` (types `pension`, `keren_hishtalmut`, `kupat_gemel`) with report fields (status, employer, fees, `details` JSON: tracks + returns, components, coverages), `asset_deposits` and `pension_reports` (the report's own totals). Imported from a report extracted to JSON: `POST /api/pension/import` or `npm run import:pension -- data/reports/<file>.json` (idempotent; the PDF and JSON stay in git-ignored `data/reports/`). "ייבוא דוח" (`web/src/components/ImportDocuments.tsx`, on /pension, /insurance, /loans): a JSON file is imported directly; a PDF / image goes to `POST /api/reports/upload` (→ `data/reports/`) and is sent to the chat, whose `import-document` skill reads it and imports through the API (`/pension/import`, `/insurance`, `/liabilities` + `/liability-snapshots` + `/scheduled`). A study fund is liquid 6 years from joining; a provident fund without a liquidity date isn't liquid.
- Stock-market investments (`/investments`, `src/server/routes/investments.ts`): `holdings` (symbol, quantity, optional buy price / date; no buy price → `baseline_price` = the price when added, the yield runs from it; `manual_price` for something with no quote). Live prices from Yahoo Finance (`src/analytics/quotes.ts`, only symbols are sent; TASE quotes in agorot → stored in ₪) cached in `quotes` (refreshed when older than a minute on page load, 5 min for `/networth`, and in the pipeline), daily closes in `quote_history` (from each holding's start; Yahoo FX rates fill days BOI hasn't published, never replace them). Valuation in `src/analytics/investments.ts`; net worth adds one `brokerage` item per broker + owner, and the closes to its month-end history.
- Logs & scrape problems: `src/log.ts` mirrors console.* and the Fastify log into `data/logs/<server|scrape>-YYYY-MM-DD.log` (14 days); `src/scrapeErrors.ts` turns an error type / message / the bank page's text into a Hebrew explanation; `scrape_runs` keeps `page_state` and `start_date` (migration 16; 17 repairs databases made by main when that was 15). Page `/logs`, API `/api/scrape/runs`, `/api/logs`.
- Chat providers: `agent_provider` setting (or `AGENT_PROVIDER`) = `claude` (default) | `gemini` | `kiro`. Gemini runs headless stream-json in `<tmp>/household-agent-gemini` (`.gemini/settings.json`: `tools.core: ["activate_skill"]`, trusted household MCP only, `GEMINI_SYSTEM_MD`); Kiro runs `kiro-cli chat --v3 --no-interactive --agent household` in `<tmp>/household-agent-kiro/<uuid>` (agent `tools: ["@household"]`, plain-text output, `--resume` per folder). Neither gets file access; both open the documents with the MCP tool `read_document` (only files in `data/policies` / `data/reports`, symlinks resolved; Gemini gets the file itself as inline data, so scans and photos work; Kiro gets the PDF's text layer via `unpdf`, so scans / photos need Claude or Gemini). Claude keeps its own `Read`. All three get the `change` tool; Kiro reports no tool calls, so the UI refreshes after every Kiro answer. Session ids are prefixed `gemini-` / `kiro-`.
- `src/server/scrapeJob.ts` — scrape started from the overview button (one at a time, in memory); the Hapoalim OTP is answered via `POST /api/scrape/otp`.
- Desktop app (`desktop/`, Electron; macOS, Windows, Linux): `main.ts` forks the server (`src/server/desktop.ts`: API + built UI on 127.0.0.1:4330 via `startServer({ webDist })` in `src/server/app.ts`, daily scrape `scheduler.ts`, daily DB backup, alert notifications) and talks to it over IPC (`desktopProtocol.ts`); window closes to the tray/menu bar. Paths come from `src/paths.ts` (`HOUSEHOLD_HOME` = `<userData>/household`, `HOUSEHOLD_APP_DIR` = resources). Bank logins: `desktop/credentials.ts`, `<userData>/credentials.json` = clear index (field names) + values encrypted by `safeStorage` (Keychain / DPAPI / libsecret), or a master password (`vault.ts`, scrypt + AES-GCM) where Linux has no keyring; decrypted only in main when a scrape asks (`setConfigProvider` in `src/config.ts`), never sent over HTTP or to the UI (`window.familycfo` in `desktop/preload.ts` only writes / lists names). First run: native import-or-fresh dialog, then the `/welcome` wizard (members → logins, each checked with `POST /api/scrape/check` = log in only, nothing saved → schedule). The build (`desktop/build.mjs`) neutralises the `import.meta.url === file://argv[1]` CLI guards — keep that pattern for CLI entry points. Packaging rebuilds better-sqlite3 for Electron, then the scripts rebuild it for the system Node.
- Scrape browser (`src/browser.ts`): an installed Chrome / Chromium / Edge, else Chrome for Testing downloaded into `<data>/browser` from Settings or the wizard (`GET /api/browser`, `POST /api/browser/download`); no browser → the scrape is refused before any login is decrypted.
- The API rejects non-loopback `Host` and foreign `Origin` headers (`src/server/web.ts`: DNS rebinding / CSRF from other pages).
- `web/` — Vite + React + Tailwind, Hebrew RTL. Global filter (member / business / tags) in `state.tsx`. Its TS config is `web/tsconfig.app.json`.

**Key rules:**
- Transaction `kind` decides what counts: `transfer`, `card_payment` and `savings` are never income/spend. A bank row like `ויזה`/`כאל` is a `card_payment` only when a scraped card's charges explain it; otherwise it is a debit purchase (expense).
- Installments count on their charge date (`processed_date`); other spend on the purchase date. Business share (`business_share_pct`) is excluded from household totals.
- `category_source`/`kind_source = 'manual'` means the user set it — rules and re-scrapes must not change it.
- Member of a row = `transactions.member_id` ?? account owner ?? shared.
- Manually entered rows (cash, paid by someone else) live on the `manual:entries` account (`kind = 'manual'`): they count as income/spend everywhere but are never a bank balance, so the forecast ignores them. Only these rows can be edited in full or deleted (`/api/transactions/manual`, `PUT /:id/manual`, `DELETE /:id`).
- Daily allowance (`src/analytics/allowance.ts`, card on the overview, `summary.allowance` / `GET /api/allowance`): the largest steady daily spend until the end of the planning period that keeps every day's bank balance ≥ the buffer — `min over days d of (balance_with_known_flows(d) − buffer) / days_to_d` (today included), minus the expected-events set-aside per day. Known flows = the forecast's scheduled items and planned bank payments, and only the certain part of each card statement (`committedCardAmount`: reported rows + installments + fixed + planned, never `typicalVariable`); the dynamic bank-spend estimate is left out. Everyday spend is counted as leaving the bank the same day (conservative).
- Expected-events fund (`/seasonal`, `src/analytics/seasonal.ts` + `hebcal.ts`, migration 18): `seasonal_events` (yearly date in the `hebrew` calendar — Intl month names, `Adar` = Adar II in a leap year, a missing 30th falls on the month's last day — or `gregorian`; expected amount; `settled_through`) and one `sinking_funds` row with `kind = 'seasonal'` holding the pot (created with the first event, left out of `savingsCapacity`'s split). Monthly set-aside = max over events sorted by date of (cumulative amount − pot) / months until it (≥ 1). An occurrence that passed after the event was created and after `settled_through` waits for "how much did it take" (`POST /seasonal/:id/settle` lowers the pot, closes its `seasonal_settle` alert). Suggested amounts: extra variable spend in the 29 days around past occurrences vs a usual day (`suggestFromHistory`).
- Month close (`/month-close`, `src/analytics/monthClose.ts`, migration 19): for a cycle that ended — accounts with rows to its end (a gap matters only if the account wasn't scraped after the end), duplicates, uncategorized expenses, confirmed bank scheduled items that didn't post (`alreadyPosted`) asked as ended / later / other, suggested links, planned items still waiting. Answers in `month_close_checks` (`ok` approves a warning). "ended" sets the item's `end_date` to the day before the cycle (undone if the answer changes). Closing writes `month_closes` with a snapshot and a signature (row count + Σ|amount|); a different signature later = "changed since closed". `monthReport` = the cycle vs the average of the complete cycles before it (`spendBaseline(…, cycle.start)`).
- Reminders (`/reminders`, `src/analytics/reminders.ts`, migration 22): `reminders` (text, `start_at` Israel local `YYYY-MM-DDTHH:MM`, repeat once / monthly / yearly — occurrences counted from `start_at`, so the 31st stays the month's last day — `href`, `last_fired_at`, `done_at`) and automatic ones computed from stored dates (insurance `end_date` and loan `end_date` 30 days ahead, a study fund's `liquidity_date` 30 days ahead, a planned item 3 days ahead). `fireDueReminders` (every minute in `src/server/desktop.ts` and `src/server/index.ts`, on wake / start, and in the pipeline) inserts alerts `reminder` (per occurrence) / `reminder_auto` (per date) and the desktop shows them right away. `alerts.href` = the screen an alert opens (Insights "לטפל בזה", the desktop notification's click); the newer alert types set it.
- Personal loans (`/iou`, `src/analytics/iou.ts`, migration 21): `iou` (direction `owed_to_me` / `i_owe`, person, amount, date, due date, `match_pattern` = text in the Bit / transfer description, default the person) and `iou_payments`. Suggestions: rows that mention the pattern, in the repayment direction, dated from the loan, up to what's left (`paymentCandidates`); a row of the loan's amount ±10 days in the lending direction (`sourceCandidates`). A row linked as the loan or a repayment becomes `kind = 'transfer'` (manual) — lending isn't spend, getting it back isn't income — and its previous kind is kept (`txn_prev_kind`) and restored when unlinked or the loan is deleted. Repaid in full = `done_at`; removing a payment reopens it. Alerts `iou_due` (past due) and `iou_payment` (a row that looks like a repayment).
- Maaser (`/maaser`, `src/analytics/maaser.ts`, `settings.maaser_cfg`, off until enabled): per cycle from `startMonth` (default 12 back) — income = `incomeOf` of the cycle's rows (net; minus income categories / description texts the user excludes) or a fixed `grossMonthly`; required = income × percent; given = spend − refunds in the donation categories (a parent includes its children; default: categories named "תרומ…" but not "…מתנות"); running balance from `openingBalance` (+ = still to give). The overview shows "נשאר לתת" when enabled.
- Charge moves (`/charge-moves`, `src/analytics/chargeMoves.ts`, migration 20): `charge_moves` rows = one recurring charge moved from `from_account_id` to `to_account_id`, or cancelled (`to_account_id` NULL). Candidates = the account's active `recurring_series` (subscription / bill / loan, ≤ 6 rows in the 130-day window, so weekly shops aren't offered). `todo` → the user ticks it → `moved` with `marked_at` → `verifyChargeMoves` (pipeline, after `refreshRecurring`; also re-checks `verified`): a charge of the same merchant (±50%) on the old account dated after `marked_at` = `failed` (alerts `move_still_on_old` / `cancel_failed`, keyed by the row); a move is `verified` by a charge on the new account (`sameMerchant`, ±25%, from 14 days before `marked_at`); a cancellation once its usual day + 5 days passed and the account was scraped after that. A charge moved on purpose doesn't raise `new_subscription`. "ביטלתי" in the subscriptions list on /insights = `POST /charge-moves {toAccountId: null, marked: true}`.
- Health check (`/health`, `src/analytics/health.ts`, `GET /api/health`): one list of `problem` / `suggestion` / `ok` rows — each company's last scrape (failures in a row, companies with an active account), backup age (desktop only, `latestBackup`), bank balances older than 3 days, cards with no paying account (`inferBillingAccounts`), duplicates in 45 days, the uncategorized share of 90 days' expenses (≥ 5% = problem), months with no rows inside a busy account's history (median ≥ 5 rows a month), suggested payback links (confirm / reject buttons), planned items a week past their date, and merchants categorized by hand ≥ 3 times to one category with no rule (a "create rule" button = `POST /rules`). Buttons are plain API calls the row carries (`actions`). "Ignore" stores the row's exact wording in `settings.health_ignore` (`PUT /api/health/ignore`); a changed wording shows it again. The menu badge = problems not ignored.
- Simulator (`/simulator`, nothing saved): `src/analytics/simulator.ts` is pure with no imports, so `web/src/pages/Simulator.tsx` imports it directly (Vite `server.fs.allow` lists only that file) and runs it as the sliders move; the API runs the same code for the chat (`GET /api/simulator/debts`). Inputs from `simulatorBase` (`GET /api/simulator/base`): per-category average over `spendBaseline`'s complete months, general funds with a goal, unarchived loans with a balance snapshot, a rate and a repayment (`monthly_payment`, else the linked scheduled item; the rest are listed as skipped). `debtPlan` month by month: interest, CPI linkage (`index_type = 'cpi'`, assumed yearly CPI), each fixed repayment, then (snowball = smallest balance first / avalanche = highest rate, CPI-linked = rate + CPI) the extra + repayments of closed debts go to the first open debt; the baseline has no extra and no roll-over. An optional early-repayment fee is a % of every shekel beyond the fixed repayments. Capped at 600 months (a repayment below the interest never ends). `cutImpact`: months to each goal at its monthly target vs with the whole cut added.
- Planned expenses (`planned_items`, `src/analytics/planned.ts`): one-offs entered before the card/bank charges them. While `status = 'planned'` they count in the forecast (card: added to the statement they land in; bank: an event), the budget and the month plan — never as actual spend. `matchPlanned` (pipeline + after edits) links them to the real row when exactly one candidate fits (same account, amount ±10%, purchase date −7..+30 days); several candidates → the user picks. "לא זה" stores the row in `rejected_txn_ids`.
- "Income of a month" is always `monthIncome()` (arrived + recurring still expected). `expectedIncome()` is only the typical-month average for savings capacity.
- Hebrew regexes can't use `\b` (JS word boundaries are ASCII-only) — use explicit lookaheads.

**Configuration:**
- Bank logins: copy `accounts.example.json` to `accounts.json` (git-ignored; `ACCOUNTS_FILE` overrides the path) — `accounts[]` with `companyId` (an israeli-bank-scrapers company id) and `credentials`; optional `categoryApiUrl` (POST `{description}` → `{category}`).
- Ports: `PORT` (API, 4310) and `WEB_PORT` (web, 5180).

**Database:**
- SQLite file: `bank.db` (auto-created and migrated on open; `BANK_DB` env overrides the path — use a copy for experiments). A new database gets default members and a default category tree (migration 14, with the card companies' category names as aliases).
- `npm run demo` builds `demo.db` with an invented household (`src/demo.ts`); `npm run dev:demo` runs the app on it.
